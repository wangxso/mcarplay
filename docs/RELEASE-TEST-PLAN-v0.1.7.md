# v0.1.7 正式发版验收测试清单

更新：2026-11-14。本文是「把 v0.1.7-test.1 收成正式版 v0.1.7」的实车/实体接收端验收清单。
它不是支持列表；只有按 `AGENTS.md` 在 `docs/CARWITH-ENTRY-FINDINGS.md` 留下带日期的证据后，某项才能记为通过。
单元测试、回环测试和模拟器结果都不能替代实车音画触控。

## 怎么用这份清单

三段式，先排雷再深测，避免四个接收端各跑一遍才发现同一个阻塞：

1. **冒烟（每台约 5 min）**：G1、G2、G3、G4、G7、G8 各做一次。任何一台连不上或没画面，先停下来查，不要继续跑专项。
2. **专项（按接收端）**：DiPlay / WinPlay / macplay 跑 T2–T4、T6；艾瑞泽 8 跑 T1 与 `ARRIZO8-PROTOCOL-REGRESSION.md` 的 A8 表。
3. **长稳与遗留**：G9–G12、S 组、T5（奔驰有实车时）。

记录方式：每台测完立刻把结果追加到 `docs/CARWITH-ENTRY-FINDINGS.md`（模板见第 6 节），报告文件留在本机。
没测的项写「未测」，不要留空，也不要把「发送计数正常」写成「画面/声音通过」。

## 0. 候选构建（先确认测的是哪个包）

正式版必须用**与最终发布包相同的提交和签名**验收。当前仓库状态需要注意三点：

1. `v0.1.7-test.1` 指向 `3a131b7`，发布资产 `mcarplay-0.1.7.apk`，SHA-256
   `44e5b1931ed80728c1e3971f86d34b146ff09509e8d7cacab8a90ffe1881ef4f`，版本 `0.1.7`、`versionCode=1070000`。
2. 该 tag **不包含** tag 之后合入 `main` 的 #59（奔驰 MB_D-PP 手动车型预设，`2b2ac6b`）。若正式版要带上它，
   必须从 `origin/main` 重新出包并重新验收，不能直接对 test.1 的 APK 打 `v0.1.7`。
3. 不要从**未合入 `main` 的分支**（例如进行中的会话层重构分支）构建发版候选包；验收包必须是
   `main` 上某个具体提交的产物，否则验收结论无法对应到发布内容。

建议做法（推荐 B）：

| 方案 | 做法 | 代价 / 风险 |
| --- | --- | --- |
| A | 直接验收 test.1 的 `mcarplay-0.1.7.apk` | 正式版要么不带 #59，要么带上未验收的 #59；发版内容与验收包不一致，不推荐 |
| B | 从 `origin/main` 当前提交出 `v0.1.7-test.2`，验收该包，正式版只多一个 CHANGELOG/README/版本号的准备提交 | 多一轮 tag 与约 20 分钟 CI，换来「验收包 = 发版内容」 |

开工检查：

```bash
git fetch origin --tags
git log --oneline -1 origin/main
git merge-base --is-ancestor v0.1.7-test.1 origin/main && echo "tag 在 main 上"
```

安装前核对包与签名。若手机上现在是 debug 包（`0.1.7-debug`），它与 release 包证书不同、无法覆盖安装；
卸载会清掉本机车型预设与配对信任，所以**正式验收建议在一台只装 release 包的手机上做**：

```bash
shasum -a 256 mcarplay-0.1.7.apk
"$ANDROID_HOME/build-tools/35.0.0/apksigner" verify --print-certs mcarplay-0.1.7.apk
adb install -r mcarplay-0.1.7.apk   # 已装 v0.1.6 正式版时应可直接覆盖
```

安装后确认界面上是 `0.1.7`（不是 `-debug`）：设置页「检查更新」里的「当前」一行会显示版本与发行标签，
本地构建显示「本地构建，未知」。若手机上装的是 test.1 的 APK，这一行应显示发行标签 `v0.1.7-test.1`；
如果显示「未知」，说明装的不是从 Release 下载的包，验收记录要写清楚来源。

每台设备开工时先记到测试记录里：日期/时区、手机型号、HyperOS、CarWith 版本、小米 CarLife 版本、
接收端型号与固件、APK SHA-256、车型适配选项（自动/手动）、是否首次配对。

> 判定分两级：**P0** = 第 1 节的 G1–G12（基本可用性与稳定性），任一接收端失败即不能发版；
> **P1** = 第 2、3 节的专项，失败时可以不发阻塞，但必须确认不是相对 v0.1.6 的新回归，并登记为已知缺陷写进 CHANGELOG。

## 1. 通用流程（G 组，四台接收端都做）

| ID | 操作 | 通过判据 |
| --- | --- | --- |
| G1 | 首次配对后连接：启动连接 → 蓝牙 iAP2 → 入网 → 发现/配对 → 会话 → RECORD | 首页卡片七层依次完成；报告里 `MILESTONE` 到 `RECORD`；无长时间 `BLOCKED_AT` |
| G2 | 画面 | 车机出现 CarWith 画面；方向、缩放正确；首页「实际/目标」帧率非零；连续 60 s 不卡死 |
| G3 | 触控 | 单点、拖动、四角点击都能落到手机对应位置；拖动不漂移 |
| G4 | 声音（开启声音） | 车机扬声器出声；手机本机静音；音量正常；报告有 `FIRST_AUDIO` 与音频包计数 |
| G5 | 仅视频 | 选择「仅视频」后连接仍成功、画面正常、无声音；报告里无音频 SETUP |
| G6 | 媒体键 | 车机上一曲/下一曲/播放/暂停/停止各触发一次；长按不重复触发 |
| G7 | 手动断开 | 车机画面立即中断；手机回未连接；报告 end 状态为 `USER_STOP`；无异常堆栈 |
| G8 | 重连 | 断开后 10 s 内再次连接成功，画面/声音/触控恢复；报告为新 attempt |
| G9 | 后台与息屏 | mcarplay 退到后台、手机息屏后连接保持 5 min；车机画面与触控不断 |
| G10 | 锁屏 | 连接中锁屏 2 min 再解锁；画面不中断；报告无 `WIFI`/`ENONET` 异常 |
| G11 | 长稳 | 连续 30 min，覆盖导航 + 音乐 + 触控；无掉线、无内存异常、无应用崩溃 |
| G12 | 导出报告 | 每条异常/每轮验收都能导出脱敏报告，报告含 APK SHA-256、版本、阶段耗时 |

## 2. v0.1.7 新增行为专项（T 组）

以下改动都没有实车证据（见 `CHANGELOG.md` 的 v0.1.7-test.1 条目），是本次验收的重点。

### T1 车机返回原车界面后重进 CarPlay（艾瑞泽 8 优先）

1. 连接成功后，在车机上点 CarPlay 图标返回原车界面（或点 CarWith「返回车机」）。
2. 确认车机切回原生界面、音频交还；手机侧屏幕流、音频、keepAlive 保持（报告 `SCREEN_OUTPUT` 显示暂停而非停滞）。
3. 再点车机上的 CarPlay 图标。

判据：主屏（有音频时含主音频）被重新拿回；屏幕流重建后重新发送 `RECORD`（艾瑞泽 8 单次 RECORD 策略下也不能被挡住）；
3 s 内车机收到画面并可触控。证据：`requestUI` → `modesChanged` → `RECORD` → 首帧写出的时间线，以及用户确认的「返回/重进」时刻。
注意：0.1.6 的艾瑞泽 8 反馈是重进后声音与方向盘失效，本项必须单独复测并记录是否仍复现。

### T2 重连 Wi-Fi 交接与 iAP2 重新协商

| 子项 | 操作 | 判据 |
| --- | --- | --- |
| T2-1 | 已配对车机首次连接 | 用完整凭据自动入网，不弹多余确认 |
| T2-2 | 断开后 30 s 内重连 | 命中缓存（目标实例 + SSID）自动入网，不合成开放热点；首页不出现新建热点的异常 |
| T2-3 | 只有 SSID 的端点（清缓存或换网络） | 走「当前网络核对 / 用户确认 / 系统 WLAN 手动加入」之一；不得静默创建一个开放热点 |
| T2-4 | 入网阶段关闭车机蓝牙 | 立即中止入网；报告为 `BT_LINK_CLOSED`（不是 AirPlay 配对失败） |
| T2-5 | AirPlay TCP 连不上（车机 AirPlay 未启动） | 报告 `AIRPLAY_CONNECT_FAILED`，不得记成配对认证拒绝 |
| T2-6 | 重连后 iAP2 必须重新协商 | 车机端确认连接恢复；报告里旧链路终止/重建有界，无重复会话残留 |

### T3 自动重连断路器

1. 故意制造快速失败：让车机在出画前断开（关车机蓝牙/AirPlay，或让 CarWith 不出流），5 min 内重复 3 次。
2. 停在第 3 次失败后的首页。

判据：首页显示「自动重连已暂停」与剩余秒数；期间不再自动发起连接；手动点「启动连接」可以立即恢复；
另换一台接收端（不同蓝牙地址）时不被上一台的暂停状态影响；杀进程重开应用后暂停状态仍保留（跨进程持久化）；
首帧发出或一次健康会话后状态清除。

### T4 诊断页通知使用权入口

1. 关闭 mcarplay 的通知使用权，进入「诊断」标签，观察「通知使用权」行，点「去开启」。
2. 在系统页授予后返回。

判据：行内状态从「未开启」变为「已开启」；点击能打开系统通知监听设置（详情页优先，失败回退列表页）；
HyperOS 上的回退路径未验证过，若回退失败记为该子项失败并保留截图。

### T5 奔驰 MB_D-PP（车主或实车可用时）

1. 干净 CarWith 进程起步，先只选「仅视频」（或开启声音后仅视频），保持 60 s。
2. 启动时直接开启声音。
3. 会话中动态开启声音。
4. 自动重连后检查音频/仅视频选择是否被保留。

判据：每条控制连接只发一次 `RECORD`；音频 SETUP 后不再补发第二条 `RECORD`；屏幕数据口不出现 16–559 ms 内的 EOF/reset；
「仅视频」选择在自动回连后不被覆盖；音频拆链时间按真实间隔记录（<10 s 记毫秒，>10 s 保留一位小数），
只有 8–12 s 才标记为 ~10 s 看门狗。若测试版本含 #59，另验手动预设「奔驰 MB_D-PP」：车机自报 `Mercedes-Benz`/未知厂牌时生效，
自报其他已知厂牌时只写 `manual.mercedes-mb-dpp-blocked` 且策略不变。

### T6 其他 0.1.7 修复项

| 子项 | 操作 | 判据 |
| --- | --- | --- |
| T6-1 | DiPlay 0.2.22 连接 | 连接稳定；不再出现 `/feedback` 500 相关症状（拿不到接收端日志时记为间接证据） |
| T6-2 | 自动播放（默认开） | 连接后由 CarWith「媒体开始」硬按键起播，不注入触摸、不切歌；已在播放的不变 |
| T6-3 | 自动播放关闭 | 设置里关闭后连接，车机不会自动起播；之后手动播放正常 |

## 6. 证据采集与工具

1. 每轮结束（成功或失败）都在首页点 **导出脱敏诊断报告**；应用异常退出则重开后立刻导出，不要先重装或清数据。
2. 报告落在 `Download/mcarplay/`，只在本机，不会自动上传。分享前检查自由文本隐私。
3. 报告里必须能读到：`app.apk.sha256`、版本名/版本号、`MILESTONE`、`STAGE_DURATIONS`、`BLOCKED_AT`、
   `COMPAT:` 规则、视音频计数。写不出这些的轮次不算证据。
4. 离线摘要与对比（`tools/`，用 `.venv/bin/python`）：

```bash
.venv/bin/python tools/analyze_diagnostics.py ~/Downloads/mcarplay/<report>.txt
.venv/bin/python tools/compare_diagnostics.py baseline.txt candidate.txt --attempts 2
```

对比脚本用于「同一场景、两版构建」的回归，例如用 v0.1.6 正式版报告做基线、候选包报告做对比；退出码 0 一致、1 有差异。
报告原文不入库（`AGENTS.md`：日志、抓包、回放素材不得提交）。

每条记录建议按下面格式追加到 `docs/CARWITH-ENTRY-FINDINGS.md`：

```text
## YYYY-MM-DD 接收端 / 手机：v0.1.7 候选包验收
- 环境：手机、HyperOS、CarWith、CarLife、接收端与固件、APK SHA-256、车型预设
- 步骤与结果：G1–G12 逐项、专项 T/S 逐项、用户对画面/声音/触控的确认
- 证据：报告编号（不回填原文）、关键阶段耗时、异常码
- 边界：哪些项没测、哪些是间接证据
```

## 7. 发版判定与动作

**可以发正式版的必要条件**（缺一条就不发）：

1. 四接收端（DiPlay、WinPlay、macplay、艾瑞泽 8）在**同一候选包**上第 1 节的 P0 项全部通过，且无相对 v0.1.6 的 P0 回归。
2. 第 2、3 节专项中没有「失败且未登记为已知缺陷」的项；专项里出现 P0 级现象（连不上、没画面、没触控）时按 P0 处理。
3. 已知问题（#51、#26、#55）如实记录在 CHANGELOG 的「已知缺陷」里。
4. 离线门禁在候选提交上通过（本地或 CI）：

```bash
./gradlew spotlessCheck :app:testStandardDebugUnitTest :app:lintStandardDebug :app:assembleStandardDebug :app:testRemoteDebugUnitTest --tests 'com.mcarplay.app.bridge.*'
.venv/bin/python -m unittest discover -s tools -p 'test_*.py'
node --test tools/debug-bridge/*.test.mjs
```

5. `CHANGELOG.md` 顶部存在**精确**的 `## [v0.1.7] - YYYY-MM-DD` 条目（英文在前、简体中文在后，含验证行与 compare 链接）。
   `tools/release_notes.py` 要求该 tag 恰好一条非空记录，签名工作流缺条目会直接失败。
6. `app/build.gradle.kts` 的 `appVersionName` 与 tag 一致（当前 `0.1.7`）；README 与 README.zh-CN 的「当前正式版」行同步更新。
7. `IMPLEMENTATION_PLAN.md`、`docs/ARCHITECTURE-REFACTOR.md` 的状态行按实际结果更新（若这些改动没有随正式版发布，不要写成已发布）。

注意：现有正式版 tag（v0.1.4、v0.1.6）都指向 `main` 上的提交，签名工作流在 **tag push** 时运行。
所以 tag 必须打在已经合入 `main` 的准备提交上，不要打在未合并的分支上，也不要对 test.1 指向的旧提交补 tag。

**发布动作**（仅在上述全部成立后）：

```bash
git switch -c release/v0.1.7 origin/main
# 改 appVersionName（如已升级）/ CHANGELOG / README / README.zh-CN / IMPLEMENTATION_PLAN，跑完整门禁
git commit -m "Prepare v0.1.7 release"
git push origin release/v0.1.7
# 开 PR、合并到 main 之后：
git switch main && git pull --ff-only
git tag v0.1.7
git push origin v0.1.7
```

若正式版内容与验收包不一致（重新出过 `-test.2`），tag 前的最后一个改动提交必须就是被验收的那个提交内容，
否则要先重跑四接收端（至少 P0 项）。

发布后核对：`gh release view v0.1.7` 的 APK 名、SHA-256、`signing-certificate.txt` 证书 SHA-256 与上一正式版一致
（v0.1.6 与 v0.1.7-test.1 的证书文件 SHA-256 均为 `efec59a0…`，可作对照），并确认未标为 Pre-release。

## 8. 不能发的情况

- 只在模拟器/单元测试上通过，没有四接收端证据。
- 任一接收端出现「能连上但没有画面」「有画面但无触控」「必须先重装才能连」。
- 艾瑞泽 8 出现新的断开后崩溃、或重进后音频/输入失效且未登记。
- 候选包与最终 tag 不是同一个提交；或签名证书与已发布版本不一致。
- 用间接证据（只有发送计数）替代用户对画面、声音、触控的确认。
